Executive Summary This analysis compares the current AALAWSNG user guide against the locked, 20-module scope recorded in the project' s Integrated Knowledge Base. The build shows substantial, genuine progress — core practice management, billing, trust accounting fundamentals, and the client portal are all implemented and localized to Nigerian legal practice (LPAR 1964, RPC 2023, FIRS VAT ). However, several requirements the knowledge base explicitly flags as binding — not optional — are either unconfirmed or absent. Of the 20 locked modules: 8 are clearly documented as built, 9 show partial coverage with at least one binding requirement un confirmed, and 3 have no evidence of implementation at all. The most consequential gap is Internal Messaging (M15), a module the specification treats as a security-critical, mandatory architectural separation — it does not appear anywhere in the current gu ide. A second cluster of gaps sits inside Trust Accounting and Document Management: the guide shows the visible, headline behavior of each module but not the specific compliance mechanisms — payment-routing logic, gateway fee handling, and API-layer docume nt visibility enforcement — that the knowledge base calls out as the highest-risk design decisions in the entire project. 3. Methodology The knowledge base's Decision Log (§3), Module Inventory (§4), and cross-cutting architectural requirements (§5–§7) wer e treated as the authoritative, locked specification. Each of the 20 modules was checked against the user guide for direct evidence of the described workflow. A module was marked “Documented” only where the guide shows the specific behavior described in th e spec, not merely an adjacent or similarly-named feature. Where the guide shows part of a module's required behavior but omits a requirement the spec calls binding, the module is marked “Partial.” This is  a documentation-based comparison: an item marked a s a gap may exist in the running application but simply not be described in the guide, and should be verified against the actual codebase before being treated as confirmed missing. 4. Priority Findings (Rationale) The findings below explain why each item was flagged, with the specific specification clause behind it. Section 6 turns these into a concrete, verify-then-act checklist for the  dev  team. P0 — Critical / Compliance-Blocking P0     Internal Messaging (M15) is  not evidenced. Spec basis: §5.2 — mandatory architectural separation from client messaging. The guide documents only the client-facing messaging channel. The knowledge base treats the internal/client messaging split as a security and professional-responsibility requirement, not a feature preference: a bug in a unified system could expose privileg ed internal communication to clients. If a staff-to-staff channel exists in the running app but isn't in the guide, document it and confirm it is architecturally separate (distinct tables/schema/service). If it does not exist, it is a missing locked-scope  module. P0     Trust payment-routing logic (§6.3.1) is unconfirmed. Spec basis: §6.3 — the single most compliance-sensitive decision in the project. The guide states only that “funds are routed according to account type.” The spec requires this routing decision (retainer/advance → trust; payment on an already-billed invoice → operating) to be explicit and auditable, not inferred silently. Confirm the a ctual decision logic and its audit logging before relying on it in production. P0     Gateway fee handling on trust deposits (§6.3.2) is unconfirmed. Spec basis: bar-rule compliance — deducting fees from trust funds is typically prohibited. Verify  Paystack   is configured so that processing fees are never netted out of a trust-destined payment. Fees must be absorbed by the firm or charged separately and disclosed — never silently reducing a client's trust balance. P0     Document visibility enforcement (§5.1) i s not shown at the API layer. Spec basis: hard security requirement — must be enforced server-side, not just in the UI. The guide shows a client-facing document vault but no internal-only classification on the staff side, and no statement that this flag is  checked at the API layer. A client-portal user must not be able to retrieve an internal document through any route, including direct API calls or ID enumeration. This needs a specific security test, not just a feature check. P0     System-wide Audit Trail  (M19) is only partially evidenced. Spec basis: §6.2 and M19 — immutable, tamper-evident logging across all state-changing operations. Only the trust three-way reconciliation has a described audit artifact (a certificate with “cryptographic tamper verificat ion”). The spec requires audit logging — who, when, what, from/to what state — across all modules, not only trust movements. P1 — High Priority P1     Staff RBAC is not shown as configurable (M20 / §7.2). Spec basis: role changes must propagate to access pe rmissions immediately; roles should be configurable, not fixed. The guide shows two fixed roles (Associate Counsel, Paralegal). Confirm whether role/permission definitions can actually be created and edited by an admin, and that permission changes take eff ect immediately rather than on next login. P1     Task & Workflow Management (M05) is not evidenced. Spec basis: distinct locked module — task assignment, per-matter-type checklists,  approval  chains. No task-assignment or checklist workflow appears in the g uide. This is separate from the calendar/deadline module and from time logging. P1     Expense Tracking (M09) is only partially covered. Spec basis: matter-linked, reimbursable-cost tracking as its own module. The guide only references “disbursements” insid e the invoicing workflow. Confirm whether a standalone expense-tracking surface exists. P1     Per-Staff Task/Workload Tracking (M12) is not evidenced. Spec basis: firm-wide capacity/utilization visibility for the principal. No cross-matter workload view is  described. This is distinct from the HR module and from per-matter task lists. P1     Hard-deadline escalation alerts (M03) are unconfirmed. Spec basis: “safety-critical” — missed deadlines carry malpractice risk. The guide describes scheduling and filtering but not escalating alerts on hard deadlines. Given the spec's own framing of this as the highest-risk item in Core Practice Management, this should be verified directly against the running app rather than left a s a documentation gap. P2 — Medium Priority / Needs Direct Verification P2     Mobile-first API design (§5.3) cannot be confirmed from a user guide. Spec basis: pagination, offline tolerance, push notifications designed in from the start. Recommend a direct API/architecture review rather than relying on user-facing documentation for this requirement. P2     Matter-type schema extensibility (§5.4) needs a data-model check. Spec basis: configurable per-matter-type fields without schema migrati ons. Confirm directly against the data model rather than the guide, which would not necessarily surface this. P2     Reporting & Analytics (M17) is folded entirely into the admin dashboard. Spec basis: firm-wide KPIs across matters, finance, staff utilizati on, and client activity. Consider whether a broader reporting surface is needed beyond the current dashboard tiles, particularly for staff-utilization and client-activity views. 6. Developer Action Plan Work through each item in order of priority. Column 1  is what to check before doing anything else; column 2 is what to build or fix only once the gap is confirmed real. ID Item Step 1 —  Dev : Verify First Step 2 — If Confirmed Missing P0-1 Internal Messaging (M15) Check  the codebase /DB for a staff-only messaging table, service, or endpoint that is distinct from client messaging. If it exists: document it in the guide and confirm the two channels are separate at the data layer (§5.2) — not a filtered view of one tabl e. If it doesn't exist: build it as a fully independent system; no client-side code path may reach it. P0-2 Trust payment-routing logic Trace what actually happens in code when a portal payment is made: is there an explicit rule distinguishing a retainer/advance deposit from payment on an already-billed invoice? If the logic exists: confirm it is logged and auditable, then document it. If  it's inferred implicitly or missing: implement the explicit rule from §6.3.1 and log every routing decision. P0-3 Gateway fee handling on trust deposits Check the  Paystack  integration  config  and a real transaction record: are processing fees ever netted out of a trust-destined deposit? If fees are already absorbed by the firm or charged separately: confirm and document. If fees are being deducted from trus t deposits: this must be fixed before any further trust-account payments are processed — it is a bar-rule violation risk, per §6.3.2. P0-4 Document visibility enforcement at the API layer Attempt to retrieve a known internal-only document via the client-portal API using its ID directly (not through the UI). Confirm the internal/client-visible flag exists in the data model at all. If enforcement already exists server-side: document it. If th e flag only exists in the UI, or not at all: implement server-side enforcement per §5.1 and add a regression test for this exact scenario. P0-5 System-wide Audit Trail (M19) Check whether create/update/delete/transfer actions outside the trust module are logged anywhere (who, when, what, from/to what state). If a general audit log exists: document its coverage and confirm it's tamper-evident. If only trust reconciliation is lo gged: extend audit logging to all state-changing operations across modules. P1-1 Configurable staff RBAC Check whether an admin can currently create/edit a role and its permissions, and whether a permission change takes effect without the user logging out and back in. If configurable already: document it. If roles are hardcoded: add role/permission management  to the admin UI and make permission changes take effect immediately (§7.2). P1-2 Task & Workflow Management (M05) Search  the codebase  for task assignment, per-matter-type checklists, or approval-chain features not mentioned in the guide. If built: document it. If not: build task assignment and configurable checklist templates per matter type. P1-3 Expense Tracking (M09) Check whether expenses/disbursements have their own data model and UI, or only exist as a line item inside invoicing. If a standalone module exists: document it. If not: build matter-linked expense tracking that feeds into invoices as disbursements. P1-4 Per-Staff Task/Workload Tracking (M12) Check for any firm-wide, cross-matter view of  who' s  working on what and capacity/utilization. If it exists: document it. If not: build a workload dashboard for the principal that doesn't require opening each matter individually. P1-5 Hard-deadline escalation alerts (M03) Check whether deadlines can be flagged as "hard" and whether escalating alerts (e.g. increasing urgency as the date approaches) actually fire. If they exist: document them. If deadlines are just calendar entries with no escalation behavior: build it — the  spec calls this safety-critical. P2-1 Mobile-first API design Review the API layer directly: pagination on list endpoints, offline tolerance for time tracking/task updates, push notification infrastructure. Document findings either way; this should be confirmed by architecture review, not by the user guide. P2-2 Matter-type schema extensibility Check the data model: can a new matter type be added with its own fields without a schema migration? Document the actual pattern used (e.g. JSON field sets, EAV, per-type tables) regardless of outcome. P2-3 Reporting & Analytics (M17) scope Check whether any reporting exists beyond the admin dashboard tiles — e.g. exportable reports, staff-utilization or client-activity views. If the dashboard is the full extent of it: decide with the firm whether a broader  reporting surface is needed for lau nch or can wait. 7. Before the P0 trust-accounting and payment-routing items  above are considered resolved, the implementation should be reviewed by a legal-technology compliance consultant against the specific rules of the bar association(s) governing the firm's practice.
